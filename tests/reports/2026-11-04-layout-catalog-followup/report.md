WebKit은 홈·남성 목록·상품 상세·로그인·구매자 체크아웃/설정/내역·관리자 배송관리 8개 route/state를 같은 8개 viewport/scale 조합으로 검사했습니다. 실제 iOS Safari 장치 검증은 아닙니다.

정의 목록은 실제 수평으로 배치된 dt/dd의 첫 텍스트 rect를 비교했습니다. 모바일에서 의도적으로 위아래로 쌓는 항목과 자연스럽게 여러 줄로 줄바꿈되는 항목은 같은 줄 정렬 불량으로 집계하지 않았습니다. 문서 가로 넘침, 뷰포트 밖으로 나간 필드, 메뉴 타깃의 양의 면적 겹침, 실제 계산된 CTA 글자색도 수집했습니다.

## 발견·수정·경고와 검증 방법 보완

- 독립 최초 build는 `PreparedProduct.key`를 React `key`와 함께 spread한 타입 오류로 실패했습니다. 제품에서 명시 props로 수정한 뒤 최종 build를 통과했습니다.
- Chromium 최초 320px·200% 디자인 시스템에서 가로 넘침 67px을 한 번 관찰했습니다. 별도 안정 상태 재접속 2회에서는 재현되지 않았습니다. 제품에서 장문 토큰·글자표·전체폭 버튼 줄바꿈과 최소 너비를 보완했고 최종 양 엔진 16조합의 넘침은 0입니다.
- 첫 전수 실행은 백그라운드 요청이 남은 `networkidle` 대기에서 30초 timeout이 났습니다. 제품 DOM 준비·폰트 bounded 대기로 수정하고 전체 288개를 다시 실행했습니다. 해당 기존 분류의 대표 사진 9개는 별도 bounded 로드 확인에서 모두 정상이며 HTTP 실패도 없었습니다.
- WebKit 빠른 문서 교체에서는 Next의 `_rsc` prefetch에 `due to access control checks` 메시지가 처음 26건, 대기 보완 재실행에서 5건 관찰됐습니다. 이를 0으로 필터링하거나 전체 엔진 오류 없음으로 보고하지 않습니다. 안정된 실제 구매자 링크 클릭 2회와 같은 8개 RSC 요청을 직접 재검증했을 때는 모두 HTTP 200이고 page error/request failure가 없었습니다. 따라서 레이아웃 GO와 자동화의 문서 생명주기 경고 WARN을 구분합니다.
- 초기 production 숨김 검사는 localhost의 308 canonical redirect를 따라 공개 운영 GET을 방문해, 로컬 production 렌더러를 검증한 근거로 쓸 수 없었습니다. 이 근거를 폐기하고 QA 프로세스의 DNS lookup에만 apex→127.0.0.1 매핑을 주입해 별도 local production 서버를 실행했습니다. OS DNS/hosts·제품 canonical 코드는 바꾸지 않았습니다. 최종 7개 응답은 localhost:3105·redirected false이며, 운영 도메인 요청은 차단해서 시도 수 0을 확인했습니다. 초기 공개 GET에도 로그인·DB 변경·PG 실행은 없었습니다.
