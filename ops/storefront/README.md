# 구매후기·배송 관리 적용 절차

작성: 2026-11-04. 최초 적용 절차와 후속 사용자 승인에 따른 운영 적용 기록을 함께 관리합니다.

## 2026-11-04 운영 적용 기록

후속 사용자 요청 `남은 작업끝내고 운영배포까지해`에 따라 운영 적용을 승인받았습니다. 대상 DB를 읽기 전용으로 확인하고 보호된 로컬 경로에 전체 custom-format 백업과 schema-only 백업을 보관했습니다. `001_additive.sql`을 forward-only로 적용하고 `002_post_verify.sql`과 현재 앱의 readiness를 확인했습니다. 기존 11개 테이블의 건수·내용 해시는 전후 같고 신규 후기·배송·이벤트는 각 0건입니다. 네 CHECK는 검증 상태이며 배송 이벤트 불변 trigger는 활성화 상태입니다. 실행 결과와 백업 메타데이터는 `tests/reports/2026-11-04-production-release/operational-schema-results.json`에 기록합니다. 백업 내용·환경파일·자격정보는 저장소에 포함하지 않습니다.

## 현재 코드의 동작

- 신규 테이블·검증된 CHECK·활성화된 배송 이벤트 불변 trigger 중 하나라도 없으면 기존 상품·주문·결제 조회를 유지하며 후기와 배송 관리만 준비 중으로 표시합니다. 연결·권한 등 다른 DB 오류는 준비 중으로 숨기지 않습니다.
- 본인의 결제 완료·배송 완료 주문 항목당 후기 한 개만 작성할 수 있습니다. 수기결제 시연 주문과 취소·결과미상 주문은 대상에서 제외합니다. 후기는 합성 생성하지 않습니다.
- 관리자는 결제 완료된 실제 주문에 송장을 등록하고 수정 사유와 배송 완료 확인 근거(5자 이상)를 기록합니다. 배송 표시는 운영자가 확인해 입력한 기록이며 택배사 API의 실시간 조회 결과가 아닙니다.
- 배송 이벤트는 같은 트랜잭션에 추가하고 수정·삭제하지 않습니다. 기존 결제 상태와 KSPAY·LAONPAY API 계약은 변경하지 않습니다.

## 승인 후 별도로 수행할 운영 적용

1. 운영 DB 백업과 대상 프로젝트·DB 식별을 확인합니다. 기존 사용자·상품·주문·원장 counts를 값·개인정보 없이 기록합니다.
2. 일회용 PostgreSQL에서 `001_additive.sql`의 최초 적용·재적용, `002_post_verify.sql`, 사용자/주문/상품 결박과 중복 후기·별점·송장 제약, 이벤트 불변성을 검증합니다.
3. 별도 승인된 시간에 `001_additive.sql`을 forward-only로 적용합니다. 기존 테이블에는 주문 항목 복합 unique index만 추가하며 기존 scalar 컬럼·결제 enum·원장은 바꾸지 않습니다.
4. `002_post_verify.sql` 결과에서 세 테이블과 PK/FK/unique/check, 활성화된 immutable trigger를 확인합니다. 기존 counts가 동일한지 대조합니다. `prisma db push`만으로는 추가 CHECK와 trigger가 만들어지지 않으므로 운영 적용을 대체하지 않습니다.
5. 독립 QA의 실제 회원 주문/후기 소유권·관리자 권한·모바일/키보드 회귀 통과 후 운영 기능을 확인합니다. 실제 거래나 배송 기록 생성은 승인된 실제 업무로만 수행합니다.

최초 코드 작업은 운영 DB를 변경하지 않았으며 이후 승인된 적용 결과는 위 기록을 따릅니다. 환경변수·키·결제 게이트는 변경하지 않았습니다. 샘플 데이터는 격리 DB에서만 사용합니다. 기존 seed의 delete/reseed는 신규 배송·후기 FK 때문에 실패할 수 있으므로 새 일회용 DB에서만 seed를 실행합니다. 운영 재시드·데이터 삭제를 수행하지 않습니다.
